# conv 前端：BRAM / 存储架构评估

> ⚠️ **本文部分结论已作废（2026-09-19 实测）**：第 3、4 节里"128 bit 宽字 = 一片 = 1280 B""一片顶 16 个 bank"
> 是**错的**——Efinix 一片 10K RAM 最多承担 20 bit 字宽，宽字靠多片并联切片（`80x128` 实测 7 片、
> `10240x120` 实测 240 片）。正确的存储结构见 **`BRAM_VERIFY.md`（V2）**。
> 仍然有效：第 1 节器件账本、第 2 节各平面字节/片数量级、原地别名思路、第 5 节带宽核算。

> 目标网络（第一步到第三步）：
> `640x480 RGB565` --2x2池化--> `320x240x3` --dw3x3+pw1x1--> `320x240x8` --池化融合--> `160x120x8`
> --dw3x3+pw1x1--> `160x120x16` --池化融合--> `80x60x16`
> 计算 8bit，一个 PE 做两次 8bit 乘法。
> 你给的预算："特征图缓存 + 中间缓存大概 160KB"。

## 0. 结论速览

| 结论 | 数字 |
|---|---|
| 器件真实 BRAM | Ti60F225 = **256 片 × 10 Kbit = 2.60 Mb = 320 KB**（Efinix 官方 Ti60 规格：10K RAM 256 blocks / 2.60 Mb；DSP 160；LE 62,016） |
| 你的方案实际占用 | **130 / 256 片 = 162.5 KB = 50.8%** —— 可行，余 126 片（157.5 KB） |
| 省 75 KB 的关键 | `160x120x8` 和 `80x60x16` 的**每行字节数都是 1280 B** → 输出行原地覆盖输入行，75 KB 不额外占存储 |
| 片型关键 | 别再用 `bram_1KB`（1024x8）做 16 bank：10 Kbit 只用到 8 Kbit（**浪费 20%**），且 16 bank 至少要 16 片。改用 **128 bit 宽字（80 字 = 1280 B = 一片整）**，一片就给 16 B/拍 |
| 带宽结论 | 输入 DDR 128bit/beat = 8 px/拍 → 输入池化只需 **4 个 max4/拍**；BRAM 读写总量 ≈ 0.8 MB/帧，远小于计算时间，**瓶颈在计算不在 BRAM** |
| 真正的紧资源 | **LUT**：上一版 `mb2_full` 已用 57,185 LUT / 60,800 XLR = **94%**，而 RAM 只用 160/256 = 62.5% |
| 2x8bit 乘法 | EFX_DSP48 `MODE="DUAL"` 原生支持：`A[18:8]xB[17:8]`(11x10)→O[36:16]，`A[7:0]xB[7:0]`(8x8)→O[15:0]，48bit 加法器分成两个 24bit 累加车道（`CONST1=48'h000001_000001`）→ 一个 PE 每拍两次 8bit MAC，互不重叠 |

## 3. 省 75 KB 的关键：原地别名（in-place aliasing）

两个视图的**行字节数完全一样**：

```
P2 视图：160 px x 8 ch  = 1280 B / 行      P2 第 r 行 在字节偏移 r*1280
P4 视图： 80 px x 16 ch = 1280 B / 行      P4 第 r 行 在字节偏移 r*1280
```

不是巧合：池化把空间减半、通道翻倍，`160x8 = 80x16 = 1280`。

**安全性证明**：产生 `P4` 第 r 行时，已经消费到 `P2` 第 `2r+2` 行（P4 行 r 依赖 P3 行 2r/2r+1，P3 行 j 依赖 P2 行 j-1..j+1）。
而 `P4` 行 r 写入的地址 = `P2` 行 r（偏移 `r*1280`）。因为 `r <= 2r+2` 恒成立，**写指针永远落后读指针 (r+2) 行，绝不会覆盖还没读的数据**。

同理第三级：`P5` 行 r = 80x32 = 2560 B = 2 行 P4，写到 P4 第 2r 行；产生 P5 行 r 时已消费 P4 到行 2r+2 → 依然安全。

**结论**：只需要一块 120 片（150 KB）的"平面"BRAM，就能装下 `160x120x8` 与 `80x60x16`（乃至 `80x60x32`，前提是平面能给出 150 KB）。这就是"中间缓存区"的全部。

## 4. 片型与布局：为什么换成 128 bit 宽字

一片 = 10,240 bit，Efinity 支持的模式利用率：

| 模式 | 每片字数 x 位宽 | 存 8bit 数据的利用率 |
|---|---|---|
| 1024 x 10（`bram_1KB` 是 1024x8，1 片只用 8 Kbit） | 1024 | **80%（旧方案在这里亏）** |
| 512 x 20 | 512 | 80% |
| 256 x 40 | 256 | **100%**（5 B/字） |
| 128 x 80 | 128 | **100%**（10 B/字） |
| 80 x 128 | 80 | **100%**（16 B/字）★ 推荐 |

旧方案 `mb2_cache.v`：`bank = 列号 mod 16`，每 bank 一片 `bram_1KB`，一次访问 16 B。
→ 得到 16 B/拍，但要 **16 片起步**，且每片浪费 20%。

新方案：**一片 = 80 字 x 128 bit = 1280 B**，一片独立完成 16 B/拍的读写（一个字就是 16 个连续字节），利用率 100%。SDP（简单双口）天然是一个写口 + 一个读口 → 正好给"生产者写 / 消费者读"。

需要 IP 带**字节使能**（`BYTEENA_ENABLE/BYTEENB_ENABLE=1`）：池化一拍只产 12 B、tile 写回只写 5 列。

### 建议的 3 块存储 IP

| IP | 形状 | 片数 | 用途 |
|---|---|---|---|
| `conv_raw_line` | 80 x 128 bit | 1 | 原始偶数行 640 px RGB565（写 8 px/beat，读回做 2x2 池化） |
| `conv_band12` | 720 x 128 bit | 9 | 12 行 x 320 px x 3ch 池化面（每行 60 字 = 960 B） |
| `conv_plane` | 9600 x 128 bit | 120 | `160x120x8` 兼 `80x60x16`（原地别名） |

（也可以合成一块 10,400 x 128 bit 的大 IP 按地址分区；分开三块更好做时序约束与仿真。）

### 地址映射

```
raw_line : {beat[6:0]}                        80 字，1 字 = 8 px RGB565
band12   : {slot[3:0], word[5:0]}             slot = 行号 mod 12，每行 60 字
           环推进：每算完一个 tile 前进 10 行 -> slot 序列 0,10,8,6,4,2,0 ...
plane(P2): {ch[2:0], row[6:0], word[3:0]}     8ch x 120row x 10 字 = 9600 字
plane(P4): {ch[3:0], row[5:0], word[2:0]}     16ch x 60row x 5 字 = 4800 字
           P4 的字节地址 = P2 的字节地址（第 3 节），所以两套视图天然重叠
```

窗口读取：一个 16 B 宽字 = 同一 (ch,row) 上 16 个连续列 → 12x12 窗口 = 12 次读（每次 16 B，用 12 B）。

## 5. 端口与带宽核算

- 输入：DDR 1 beat/拍 = 8 px。偶数行写 `raw_line` 128 bit/拍；奇数行到达时读回 128 bit/拍 + 池化输出 **4 px/拍 = 12 B/拍** 写 `band12`。
  - 12 B/拍 跨字 → 攒 4 拍（48 B = 3 字）后连续写 3 个字，或直接给 IP 开字节使能按 16 B 对齐攒写。
- `band12`：一个 tile = 10 行 x 60 字 = 600 字写；窗口读 3 ch x 144 B。
- `plane` 写：L1 池化写 200 B/tile x 768 tile = 153,600 B；L2 池化写 400 B/tile x 192 tile = 76,800 B。
- 窗口读：L1 3ch x 768 tile x 144 B ≈ 0.33 MB；L2 8ch x 192 tile x 144 B ≈ 0.22 MB。
- 按 16 B/拍折算：全部写 230,400/16 = **14,400 拍**；全部读 ≈ 0.55 MB/16 = **36,000 拍**；而整帧计算 **~361,000 拍**（上一版实测）。→ 读写可以完全藏在计算背后。

**唯一的硬约束**：12x12 窗口不可能一拍从 BRAM 拿全（要 100 个读口）。窗口必须"分拍装入寄存器"——沿用 `feature_map_12_12` 的做法（144 x 8bit = 1152 FF/通道），12 拍装一行、共 12 拍/通道。

## 6. 计算侧核对（8bit、两次乘法/PE）

- DDR 侧：614,400 B/帧 ÷ 16 B/拍 = **38,400 拍 = 0.19 ms @200MHz**，不是瓶颈。
- MAC 数（纯算术）：

| 级 | dw3x3 | pw1x1 | 小计 |
|---|---|---|---|
| L1 (320x240x3→x8) | 76,800 x 3 x 9 = 2.07 M | 76,800 x 8 x 3 = 1.84 M | 3.92 M |
| L2 (160x120x8→x16) | 19,200 x 8 x 9 = 1.38 M | 19,200 x 16 x 8 = 2.46 M | 3.84 M |
| L3 (80x60x16→x32) | 4,800 x 16 x 9 = 0.69 M | 4,800 x 32 x 16 = 2.46 M | 3.15 M |
| 合计 | | | **10.9 M MAC** |

- 100 PE x 1 MAC = 100 MAC/拍 → 109,000 拍；100 PE x 2 MAC = 200 MAC/拍 → **54,500 拍**。
- 上一版实测 361,344 拍（L1 125 / L2 745 / L3 2548 拍每 tile），说明**调度开销把 MAC 利用率压到 ~30%**：复用模式每通道 12 拍、pw 逐通道累加、量化、窗口装载、写回都占拍。→ 想提速，优先做 ① DUAL 模式两次 MAC ② 窗口装载与计算重叠（mb2 已有雏形）③ tile 间不空转。

## 7. 与"第一步：数据获取"的对应

在 `rtl/conv/` 落地的第一步（接口照 `mb2_top`：`clk/rstn/start` + `w_read_*_channel1` + `done`）：

1. `conv_pool_max4.v` —— 单棵 4 输入比较树（R/G/B 三通道 8bit 分别取最大后重新打包），两级流水打拍。
2. `conv_pool_arr.v` —— ROWS x COLS 参数化的 max4 阵列（默认 **5x5 = 25 棵**，给后面 `10x10 -> 5x5` 池化用；输入池化例化成 **1x4**）。
3. `conv_raw_line.v` / `conv_band12.v` —— 两个 BRAM IP 的封装（宽字 + 字节使能）。
4. `conv_in_dma.v` —— DDR 读 FSM + 2x2 池化 + 写 `band12`（12 行环，每次前进 10 行）。
5. `conv_tb.v` + `filelist.f` + `sim_conv.do` + `run.bat` —— ModelSim 一键，黄金模型逐字节自检（照 `mb2_tb` 风格）。

**输入池化的切分（已被器件定死）**：DDR 每拍 8 px → 2 行 x 8 列 = **4 个 max4/拍 = 4 个池化像素/拍**。
每拍 96 个像素（每行）不可能：单读口最宽 1024 bit = 64 px/拍，而且 DDR 只给 8 px/拍；96 也不整除 640。

## 8. 风险与待确认

1. **LUT 预算**：上一版 94%。新结构新增的窗口寄存器（FF）和比较树（LUT）要控制；必要时把 5x5 阵列做成 1x4 / 4x5 复用。
2. **band12 环的读写指针**：生产者（池化）写 10 新行前，消费者（L1）必须已经消费完上一 tile → 需要生产者/消费者握手（否则静默数据错）。
3. **IP 要重新生成**：现有 `ip/ram_1024_64`（无字节使能、64 字深）和 `bram_1KB`（1024x8）都不合适；需要用 `efx_ipmgr` 按第 4 节的形状生成 3 块 IP。`ip/` 目录已被 `.gitignore` 忽略，所以**生成脚本必须入库**（`rtl/conv/gen_ip/*.json` + `gen_ip.bat`）。
4. **P0 = 320x240x3 全图方案不可行**：225 KB = 180 片，再加 plane 120 片 = 300 片 > 256，所以 12 行带是必须的。
5. **第三个池化级**：`80x60x32` 全图 = 120 片，与前面合计 250/256（97.7%），基本没有余量；如果后面还要加层，需要把 L3 输出降到 DDR 或改成分块。
